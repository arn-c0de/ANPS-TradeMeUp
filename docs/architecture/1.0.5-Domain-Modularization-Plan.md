# Domain Modularization Plan — from "trading tool" to "news-to-prediction platform"

Status: proposal / idea plan. Nothing here is implemented yet.
Target version: 1.1.x (staged), first non-trading pack: `cybersec`.

## 1. Goal

Today the system is one hard-wired pipeline: financial RSS → LLM analysis → tickers →
impact/surprise scores → market predictions → candlestick charts → trading simulation.

The valuable part of that pipeline is **not** finance. It is the generic loop:

```
feeds → dedupe/quality → LLM understanding → entity resolution → impact & surprise
      → regime/decay context → prediction over a horizon → outcome evaluation → calibration
```

That loop applies unchanged to any domain where public text is a leading indicator of a
measurable future state. Cyber security is the strongest second case: advisories, exploit
publications and threat-intel blogs are the "news", CVEs/vendors/actors are the "entities",
and "did this get exploited in the wild" is the ground truth that replaces "did the price move".

The goal of this plan is to split the codebase into:

- **core** — domain-agnostic pipeline, storage, agents, GUI shell, evaluation machinery
- **domain packs** — everything finance-specific today, plus a new cyber security pack

and to make adding a third domain (e.g. supply chain disruption, energy grid, epidemiology,
regulatory watch) a matter of writing one pack, not forking the app.

Rough coupling audit (`grep -riEl "ticker|market|stock|earnings|sector|portfolio|trading" src`):
**57 of 102 Python files** mention finance concepts. But the coupling is very unevenly
distributed, and most of it is shallow (naming, prompts, one config file), not structural.

## 3. Target architecture

### 3.1 Layout

```
src/
  core/
    ingestion/          # feed fetching, dedupe, rate limiting (any source type)
    agents/             # base classes + the domain-agnostic agents
    pipeline/           # stage orchestration, batch sizing, scheduling
    models/             # generic tables: raw_news, processed_news, entities,
                        # entity_relations, impact_scores, predictions, outcomes,
                        # entity_metrics, regimes, quality, logs
    services/           # llm_service, calibration, performance, caching
    evaluation/         # outcome resolution, backtests, calibration curves
    gui/                # shell, layout, theming, tab registry, generic components
    domain.py           # DomainPack protocol + registry
  domains/
    trading/            # everything from section 2.3 + finance prompts/feeds/resolvers
    cybersec/           # new
    _template/          # skeleton for a new domain, used by the conformance tests
config/
  domains/
    trading/{domain.yaml, feeds.json, prompts/, taxonomies/}
    cybersec/{domain.yaml, feeds.json, prompts/, taxonomies/}
```

### 3.2 The `DomainPack` contract

One object per domain, discovered by name from `ACTIVE_DOMAINS` (a new setting), so the pipeline
never imports a domain module directly.

```python
# src/core/domain.py  (sketch)

class DomainPack(Protocol):
    name: str                      # "trading" | "cybersec"
    display_name: str
    version: str

    # --- configuration ---
    def config(self) -> DomainConfig: ...          # horizons, thresholds, batch sizes
    def feeds(self) -> list[FeedSpec]: ...         # RSS + non-RSS sources
    def prompts(self) -> PromptRegistry: ...       # keyed by task: understanding, entities, scenarios
    def taxonomies(self) -> Taxonomies: ...        # entity types, event types, relation types

    # --- pipeline hooks ---
    def entity_resolver(self) -> EntityResolver: ...       # text -> domain entities
    def impact_model(self) -> ImpactModel: ...             # (news, entity) -> impact 0..1 + breakdown
    def surprise_model(self) -> SurpriseModel | None: ...
    def signal_source(self) -> SignalSource: ...           # entity -> ground-truth metric series
    def predictors(self) -> list[Predictor]: ...           # produce Prediction rows
    def outcome_evaluator(self) -> OutcomeEvaluator: ...   # prediction -> realised outcome
    def downstream(self) -> list[DownstreamModule]: ...    # trading sim / exposure sim / none

    # --- presentation ---
    def gui_tabs(self) -> list[TabSpec]: ...
    def chart_adapters(self) -> list[ChartAdapter]: ...
```

Five interfaces carry almost all the domain weight:

1. **`EntityResolver`** — finance: company → ticker. cyber: CVE-ID regex, CPE/vendor dictionary,
   threat actor & malware aliases (MITRE ATT&CK / MISP galaxy), LLM fallback for novel names.
2. **`SignalSource`** — the biggest conceptual generalization. Today `src/services/market_data.py`
   returns OHLCV. Generalize to: *for entity E, give me the time series of metric M*. Prices are
   one metric; EPSS score, KEV membership, exploit-availability, ransomware victim counts are others.
   This is what makes labelling, evaluation and charting domain-independent.
3. **`Predictor`** — emits a `Prediction` with a generic outcome distribution instead of up/flat/down.
4. **`OutcomeEvaluator`** — resolves the prediction against the `SignalSource` once the horizon passes.
5. **`ImpactModel`** — already nearly generic; needs its dimensions from config.

### 3.3 Data model generalization

Most tables survive. The changes:

| Today | Change |
| --- | --- |
| `entities.entity_id String(50)` | Already generic enough — `AAPL`, `CVE-2026-1234`, `vendor:microsoft`, `actor:APT29` all fit. Add `domain` column + composite uniqueness. |
| `entity_type`, `exposure_type`, `relationship_type` | Free-text already; validate against the pack's taxonomy instead of hardcoded lists |
| `predictions.direction_probabilities` | → `outcome_probabilities` (JSONB, arbitrary labelled classes: `{up,flat,down}` vs `{exploited,not_exploited}`) |
| `predictions.expected_return` | → `expected_magnitude` (`{mean,median,p25,p75,p95}` + a `unit` field: `pct_return`, `epss_delta`, `victims_per_week`) |
| `prediction_outcomes.actual_return` / `sharpe_contribution` | → `actual_magnitude`, plus a JSONB `domain_metrics` for pack-specific scores |
| `market_data` (ticker, OHLCV) | Split: generic long-format `entity_metrics(domain, entity_id, timestamp, metric, value, metadata)` in core; the OHLCV table stays in the trading pack |
| `signal_decay_models`, `market_regimes`, `impact_scores`, `surprise_scores` | Keep; add `domain` column, rename `market_regimes` → `environment_regimes` |
| `trading_simulation*` | Move to the trading pack's own module/migration |

Add `domain VARCHAR` + index to every shared table so one database can host several domains.
Alternative (per-domain schema or per-domain database) is cleaner isolation but multiplies
migration and ops work; recommend the `domain` column, with a per-domain Postgres schema kept as
an escape hatch if data volumes diverge.

Backwards compatibility: keep the old column names as SQLAlchemy synonyms/properties for one
minor version (the codebase already does this for `Prediction.predicted_direction`), and ship an
Alembic migration that backfills `domain = 'trading'` for all existing rows.

### 3.4 Configuration

Everything currently baked into agent constants moves to `config/domains/<name>/domain.yaml`:

```yaml
name: cybersec
display_name: Cyber Threat Intelligence
horizons: ["7d", "30d", "90d"]          # trading: 1d, 5d, 20d
prediction:
  outcome_classes: [exploited, not_exploited]
  magnitude_unit: epss_delta
  min_impact_threshold: 0.35
impact_dimensions:
  severity_weight: 0.35                  # trading: news_importance
  exposure_weight: 0.25                  # how widely deployed the product is
  exploitability_weight: 0.25            # trading: surprise_factor
  regime_weight: 0.15                    # active-campaign environment
regime_axes: [campaign_intensity, patch_cycle_phase, zero_day_pressure]
llm:
  enable_fact_checking: true
  enable_scenarios: true
```

The `enable_*` flags in `src/config/settings.py` become per-domain, not global.

## 4. The `cybersec` pack, concretely

### 4.1 Sources (not all are RSS — `FeedSpec` needs a `kind`)

| Source | Kind | Gives us |
| --- | --- | --- |
| CISA Known Exploited Vulnerabilities (KEV) | JSON catalog | **The ground-truth label**: this CVE is exploited in the wild, with a date |
| FIRST EPSS daily scores | CSV | Daily numeric exploitation-probability series per CVE — the price analogue |
| NVD CVE API 2.0 | JSON API | CVE metadata, CVSS, CPE (affected vendor/product) |
| GitHub Security Advisories | API/RSS | Package-level advisories, ecosystem mapping |
| Vendor advisories: MSRC, Cisco, Oracle CPU, Red Hat, Ubuntu USN, Adobe | RSS/API | Patch events, severity claims |
| Exploit-DB, Packet Storm, Metasploit module commits | RSS/git | Exploit-availability event with a date |
| Threat-intel blogs: Talos, Unit 42, Mandiant, Recorded Future, Microsoft MSTIC | RSS | Actor/campaign narrative, TTPs, targeting |
| News: BleepingComputer, The Hacker News, Krebs, SecurityWeek, The Record | RSS | Volume/attention signal, breach reporting |
| Ransomware leak-site trackers (e.g. ransomwatch) | JSON | Victim counts by sector/country over time |
| MITRE ATT&CK (STIX bundle) | Static import | Technique taxonomy for tagging |

The existing `IngestionAgent` handles RSS and one JSON API already; it needs a small
`SourceAdapter` abstraction (`rss`, `json_api`, `csv_snapshot`, `git_log`) rather than a rewrite.

### 4.2 Entities and relations

- Types: `cve`, `vendor`, `product`, `cpe`, `threat_actor`, `malware`, `campaign`,
  `technique` (ATT&CK ID), `sector`, `country`, `package` (ecosystem+name)
- Relations: `affects` (cve→product), `exploits` (malware→cve), `attributed_to`
  (campaign→actor), `targets` (actor→sector/country), `supersedes`, `bundled_in`

Resolution is *easier* than finance in one respect (CVE IDs and CPE strings are canonical
identifiers, no fuzzy ticker matching) and harder in another (actor aliases are a mess —
APT29 / Cozy Bear / Midnight Blizzard / NOBELIUM; use a MISP-galaxy-style alias table plus LLM
fallback, mirroring how `entity_mapping_agent` already blends dictionary + LLM).

### 4.3 What replaces "predict the price move"

The prediction targets that are actually *labelable* from the sources above:

1. **P(CVE X exploited in the wild within 7/30/90 days)** — label from KEV addition date or
   EPSS crossing a threshold. This is the flagship prediction and it maps 1:1 onto the existing
   `outcome_probabilities` + horizons + calibration machinery.
2. **Expected EPSS trajectory** for a CVE — a numeric magnitude prediction, directly analogous to
   expected return, and it reuses the existing time-series charting untouched.
3. **P(exploit code published within N days)** — label from Exploit-DB/Metasploit publication.
4. **Vendor/product risk forecast** — expected count of critical advisories per vendor next 30d.
5. **Sector/geo targeting forecast** — next likely targeted sectors for an actor or malware
   family, labelled against ransomware victim counts and incident reporting.
6. **Asset-inventory exposure forecast** (the downstream module) — given a user-supplied
   inventory (CPE list / SBOM), the expected number of newly-exploited CVEs affecting it and a
   prioritized patch order. This is the cyber counterpart of `src/simulations/trading_simulator.py`:
   same shape (a portfolio, a risk model, a ranked action list), different semantics.

Start with a heuristic predictor (CVSS + EPSS + exploit availability + news volume + vendor
prior + attention velocity), exactly as `PredictionAgent` falls back to heuristics today, then
train the XGBoost path on KEV labels once enough history is accumulated. The existing
`confidence_calibration_agent` and `model_performance_monitor` work on the new target with no
changes beyond field names.

### 4.4 What replaces the chart tab

The charts tab is the most trading-shaped part of the GUI, but the underlying machinery
(time series + overlays + infinite scroll) is reusable. The pack supplies view specs:

- **Threat timeline** — CVE disclosure → advisory → PoC → exploit → KEV addition, per CVE,
  as a horizontal event track (reuses the overlay/annotation code)
- **EPSS trajectory chart** — plain line chart against `entity_metrics`; the current chart
  component works as-is once the `SignalSource` is generic
- **Risk heat matrix** — vendor × severity, or sector × actor, cell = predicted risk
- **ATT&CK technique heatmap** — observed technique frequency over time
- **Actor → target Sankey** — attribution and targeting flows
- **Exposure table** — the user's inventory ranked by predicted exploitation probability

Candlesticks stay in the trading pack. `src/gui/tabs/__init__.py`'s hardcoded tab list becomes
a registry populated from `pack.gui_tabs()`, plus a domain switcher in the shell header.

## 5. Migration phases

Each phase must leave the app running and the test suite green. No big-bang branch.

**Phase 0 — Guardrails (small).** Write a domain-conformance test suite that exercises the
pipeline through a fake `_template` pack with two entities and a synthetic signal source. This
is the thing that will catch every accidental finance assumption in the phases below. Also
snapshot current pipeline outputs as regression fixtures.

**Phase 1 — Introduce the seam (no file moves).** Add `src/core/domain.py` with the protocol and
registry, plus an `ACTIVE_DOMAIN`/`ACTIVE_DOMAINS` setting. Implement a `trading` pack that
simply delegates to the existing modules. Agents start receiving their pack instead of reading
globals. Behaviour unchanged.

**Phase 2 — Externalize configuration.** Move feeds, prompts, event taxonomy, entity types,
horizons, impact weights, thresholds and the `enable_*` flags into `config/domains/trading/`.
Prompts get a `{domain_role}` header instead of "You are a financial news analyst".

**Phase 3 — Data model.** Alembic migration: add `domain` columns, rename the prediction JSONB
fields with compatibility properties, create `entity_metrics`, move `market_data` behind
`SignalSource`. Backfill `domain='trading'`. This is the highest-risk phase — do it alone, with
a database backup (`scripts/pg_backup.ps1` / `scripts/README_PG_BACKUP.md`) and a rehearsed rollback.

**Phase 4 — Physical split.** Mechanically move files into `src/core/` and `src/domains/trading/`
with import shims for one release. Update `docs/STRUCTURE.md`. Mostly `git mv` + import fixes.

**Phase 5 — `cybersec` MVP.** Ingestion (KEV + NVD + EPSS + 5 advisory feeds + 5 news feeds),
entity resolver (CVE/CPE dictionary + actor aliases + LLM fallback), impact model, heuristic
exploitation-probability predictor, KEV-based outcome evaluator. No GUI beyond the generic tabs.
This phase is the real test of the abstraction — expect it to send corrections back into core.

**Phase 6 — GUI pluggability.** Tab registry, chart adapters, domain switcher; cyber views from
section 4.4. Trading tabs move into the trading pack unchanged.

**Phase 7 — Multi-domain runtime.** Run both packs concurrently: per-domain worker profiles in
`docker-compose.yml`, per-domain schedules and LLM token budgets, per-domain dashboards.

**Phase 8 — Trained models & downstream.** XGBoost on accumulated KEV labels, calibration curves
per domain, asset-inventory exposure simulation.

Rough sequencing: phases 0–4 are refactor-only and can land incrementally over several releases;
phase 5 is where the second domain becomes real. Phases 1–4 carry no user-visible change, which
is exactly what makes them safe to interleave with normal feature work.

## 6. Naming

The repo is `ANPS-TradeMeUp` and the README calls it "a multi-agent news-to-market prediction
system". Post-split, `ANPS` (Agentic News Prediction System) is the platform and TradeMeUp is
the trading pack — worth deciding early, because it shapes package names, the Docker image tag,
the `User-Agent` string in `IngestionAgent`, and the GUI title. Suggested: keep the repo name,
rename the Python package concept to `anps.core` + `anps.domains.*` in docs, and let the GUI
title come from the active pack's `display_name`.

## 7. Risks and non-goals

**Risks**

- *Leaky abstraction*: designing the interfaces against only one existing domain almost
  guarantees finance-shaped hooks. Mitigation: build the `cybersec` resolver and signal source as
  a throwaway spike **before** freezing the protocol in phase 1.
- *Data migration*: phase 3 touches every table. Mitigation: backup, rehearsed rollback,
  compatibility properties, and a read-only verification pass over row counts and sample rows.
- *Prediction semantics drift*: "expected return" and "P(exploited)" are not the same kind of
  claim; forcing them into one column risks meaningless aggregate statistics. Mitigation: the
  `unit` field is mandatory, and cross-domain aggregation is explicitly forbidden in the
  performance service.
- *LLM cost doubling*: two domains, two ingestion streams. Mitigation: per-domain token budgets
  and per-domain `enable_*` flags (already the pattern in `settings.py`).
- *Scope creep*: the refactor can absorb unlimited time. Mitigation: phase 5 is the success
  criterion — if a cyber prediction with a KEV-verified outcome appears in the GUI, the
  abstraction works; polish afterwards.

**Non-goals for this plan**

- Multi-tenancy or per-user domain isolation
- Replacing Postgres/Dash/FastAPI
- Real-time streaming ingestion
- Turning the cyber pack into a security product (no scanning, no remediation execution) —
  it forecasts and prioritizes, it does not act

## 8. Success criteria

1. A new domain can be added without editing any file under `src/core/`.
2. `src/domains/trading/` produces byte-identical predictions to today's pipeline on the
   regression fixtures from phase 0.
3. The `cybersec` pack produces exploitation-probability predictions whose outcomes are
   automatically resolved against KEV, with a calibration curve rendered by the *existing*
   calibration agent.
4. `grep -riE "ticker|earnings|portfolio" src/core/` returns nothing.
5. Both packs can run concurrently in one stack against one database.

## 9. Open questions

- One database with a `domain` column, or a schema per domain? (Recommendation: column first,
  schema later if volumes diverge.)
- Should packs be in-repo packages or installable plugins discovered via entry points? In-repo is
  simpler; entry points allow private/proprietary packs later.
- Does the cyber pack need per-user asset inventories (which implies auth and storage of
  sensitive infrastructure data), or does it stay generic-population-level for v1?
  Population-level is the safer v1 and avoids holding customer attack surface data.
- Which cyber prediction is the flagship for phase 5 — exploitation probability (best labels,
  clearest value) or sector targeting (more novel, weaker labels)? Recommendation: exploitation
  probability.
